# 戦法・囲いカタログの追加方法

`app/lib/data/formations.json` が名前・図鑑・エフェクト・判定の共通データです。現在は409項目を収録し、そのうち189項目が自動判定に対応しています。IDを別のTypeScriptファイルへ登録する必要はありません。

カタログの `version` は2です。基本形だけでなく派生・旧定跡・奇襲・駒落ちも収録し、囲いと戦法の役割が異なる項目は区別します。同じ役割の名称の重複は認めず、確認できた別名は `aliases` に入れます。収録数を「独立した戦法の総数」や「自動判定の対応数」として扱いません。

`recognition: null` は名称・系統・参照資料を収録した参考項目です。読み方・解説・配置を未確認のまま補わず、必要な検証を済ませた項目から判定ルールを付けます。図鑑では「図鑑のみ」と表示し、発見数の分母にも、自動判定・棋譜記録・保存データの有効IDにも含めません。

`formations.schema.json` を同じディレクトリに置いているため、対応するエディタでは入力補完と形式の検証ができます。アプリ起動時にも形式・座標・IDの重複・発展関係などを検証します。不明な条件名はエラーになり、無視して判定を通すことはありません。

## 基本の追加例

```json
{
  "id": "taka_mino",
  "name": "高美濃囲い",
  "reading": "たかみのがこい",
  "kind": "castle",
  "family": "美濃系",
  "parentId": "mino",
  "aliases": ["高美濃"],
  "tagline": "金を高く、守りを厚く。",
  "description": "美濃囲いの５八の金を４七へ進めた形。",
  "example": [["K", 2, 8], ["S", 3, 8], ["G", 4, 9], ["G", 4, 7]],
  "sources": ["https://shoginote.com/castles"],
  "supersedes": ["mino"],
  "recognition": {
    "mirror": true,
    "patterns": [
      { "pieces": [["K", 2, 8], ["S", 3, 8], ["G", 4, 9], ["G", 4, 7]] }
    ]
  }
}
```

例のIDは既に登録されています。別の形を追加するときは新しいIDにします。IDは図鑑や対局結果に保存するため、公開後は安易に変更しません。

## 座標と駒

座標はすべて先手から見た `[筋, 段]` の数字1〜9です。内部の行列インデックスではありません。後手の判定時には共通処理が180度回転します。

`["S", 3, 8]` は先手なら３八の銀、後手なら７二の銀です。`mirror: true` はこれに加え、筋を左右反転した形も対象にします。相手の駒の条件も、同じ自分側の座標系を使います。

| 駒 | P | L | N | S | G | B | R | K |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 種類 | 歩 | 香 | 桂 | 銀 | 金 | 角 | 飛 | 玉 |

盤上の駒は未成りに限って一致します。成銀を銀として数える判定にはなりません。

## 表示データ

- `family` は図鑑の大分類、`parentId` は親の項目のIDです。親へ移動するためのリンクに使います。発展の優先順位を表す `supersedes` とは別で、循環した親関係は認めません。
- `aliases` は別名や表記揺れです。検索対象になりますが収録数には加算しません。
- `name`・`reading`・`tagline` はカットインと図鑑で使います。
- `description` は本アプリで認識する形を説明します。一般論だけでなく、対象外になる形が分かるように書きます。
- `example` は図鑑に描く代表的な配置です。判定条件より多くの駒を示すこともできます。
- `sources` は形や手順を確認した資料のURLです。アプリが外部の内容を取得して判定することはありません。

## 判定条件

`recognition.patterns` のいずれか一つに一致すれば成立します。個々のパターン内では、指定した条件をすべて満たす必要があります。

| フィールド | 意味 |
| --- | --- |
| `pieces` | 必須の自分の駒。形式は `[駒種, 筋, 段]`。 |
| `opponentPieces` | 必須の相手の駒。座標の見方は `pieces` と同じ。 |
| `originals` | 最初から持っていた駒の移動先。形式は `[駒種, 元の筋, 元の段, 現在の筋, 現在の段]`。現在位置は `pieces` にも指定する。 |
| `history.moves` | 実際に指した手。形式は `[駒種, 移動元の筋, 移動元の段, 移動先の筋, 移動先の段, 取った駒種（任意）]`。駒打ちは含まない。 |
| `history.bishopExchange` | `any` は最初の角同士の交換と直後の取り返しを確認。`before-pawn-exchange` はさらに両者の飛車先交換より前であることを確認。 |
| `history.staticRooks` | `true` のとき、両者の最初の飛車が生存し、それぞれ元の筋を離れていないことを確認。 |
| `history.bishopsPresent` | `true` のとき、両者の最初の角が未成りで盤上に残っていることを確認。 |
| `history.pawnExchanges` | `both` は両者、`self` は自分について、最初の飛車先の歩による進出・相手歩の捕獲・最初の飛車の取り返しを確認。 |
| `history.firstMove` | 自分の最初の手を確認。形式は `history.moves` の一手と同じ。嬉野流では最初の着手が６八銀であることを確認。 |
| `history.opponentFirstMove` | 相手の最初の着手を、相手自身の座標系で確認。パックマンでは相手の初手７六歩を確認。 |
| `history.orderedMoves` | 指定した自分の手が順番どおりに現れることを確認。間にほかの手は入れられる。 |
| `history.opponentMoves` | 相手の実際の着手。こちらも相手自身を先手側へ回転した座標系を使う。`opponentPieces` は自分側の座標系なので区別する。 |
| `history.drops` | 実際に打った駒と移動先。形式は `[駒種, 筋, 段]`。 |
| `history.rookFiles` / `opponentRookFiles` | 生存する最初の飛車の現在の筋。相手側は相手自身の座標系。 |
| `history.rangingRooks` | `self` / `opponent` / `both`。最初の飛車が自陣八段目から５〜９筋へ横移動したことを確認。中段の浮き飛車や最下段の地下鉄飛車は含めない。 |
| `emptySquares` | `[筋, 段]` の配列。自分・相手どちらの駒もないことを確認。 |
| `requires` | 別の対応済み項目の現在の成立条件も満たすことを要求。過去に発見した記録では代用しない。循環・未対応IDはエラー。 |

戦法には `recognition.maxOwnMoves` を必ず指定します。相手の手を含まない自分の着手数です。通常は30、早石田・新石田流は8、超速は12です。`owner` があれば先手・後手の指定も確認し、`minOwnMoves` があればその着手数まで待ちます。囲いには指定せず、対局全体で認識します。囲いが `requires` で戦法へ依存すると戦法の期限を引き継いでしまうため、この依存は検証時に拒否します。左右反転する親を使う派生には玉の位置も明記し、反対側の親と混ざらないようにします。

駒の位置だけで区別できない戦法には履歴条件を付けます。たとえば角を一方的に取った局面を角換わりと呼んだり、交換のない盤面を横歩取りと呼んだりしないためです。新しい履歴条件が必要な場合は、JSON Schema・読み込み時の検証・共通の判定処理を合わせて拡張します。

## 発展関係

`supersedes` は、より具体的な形が優先する下位のIDです。たとえば高美濃には `mino`、銀冠には `taka_mino` を指定します。関係は推移的にたどるため、銀冠から片美濃まで列挙する必要はありません。

同じ着手で複数が一致すると、発展した形だけを演出・登録します。異なる着手で片美濃→美濃→高美濃→銀冠と組めば、それぞれを発見できます。発展形を一度記録した後に囲いを崩しても、下位の形を初めて獲得する扱いにはなりません。

## 追加後の確認

1. 資料で基本配置と手順を確認し、JSONへ追記する。
2. `tests/formations.test.mjs` または `tests/expanded-formations.test.mjs` に、カタログの座標をコピーするだけではない組み上げ手順を加える。現在のテストは自動判定に対応した全IDに手順があることも確認する。追加分の座標手順は `tests/expanded-formation-fixtures.json` にあり、判定パターンから盤面を生成しない。
3. 先手・後手、必要な駒がない場合、履歴がない場合、類似形との区別、発展関係を確認する。
4. `npm test`・`npm run lint`・`npm run build` を実行し、図鑑とカットインをブラウザで確認する。

既存の発見はそのまま残り、図鑑の総数・検索・絞り込みはカタログから自動的に更新されます。

## 参考項目を先に収録する場合

最低限の項目は `id`・`name`・`kind`・`family`・`sources`・`recognition: null` です。親や別名が確認できれば `parentId`・`aliases` も指定します。空の判定パターンや推測した配置で対応済みに見せることはしません。

名称資料は [戦法の分類一覧](https://ja.wikipedia.org/wiki/将棋の戦法)、[囲いの分類一覧](https://ja.wikipedia.org/wiki/囲い)、[囲い事典の掲載項目を検討した書評](https://rocky-and-hopper.sakura.ne.jp/Kisho-Michelin/8399/978-4-8399-7450-3.htm)、[現代の図鑑の掲載名称を記録した記事](https://note.com/rekka_whitestone/n/nfdc2ce12c932) などを参照しています。転載するのは名称などの事実に限り、図版・カード画像・説明文・ランキングは転載しません。各レコードの `sources` から参照元を確認できます。

自動判定に進めるときは読み方・対象形・履歴条件を確認し、先手・後手の実際の組み上げ手順と誤判定のテストを追加します。参考項目には判定テスト用の架空の形を作りません。現在の自動判定189項目はすべて独立した組み上げ手順で検証しています。

[将棋城の囲い教材](https://shogicastle.com/ja/kakoi/)・[戦法教材](https://shogicastle.com/ja/senpou/) の公開手順・配置を追加の照合資料に使い、各項目とテスト手順へ個別ページの出典を保存しています。説明文と判定処理は本アプリ用に作成し、外部のプログラム・図版・解説文は取り込んでいません。既存の出典も各項目に保持します。

両者の形で決まる戦型は、相手の着手で成立する場合があります。Reducerは着手ごとに両側を判定し、同じ側の同じ項目を重複して記録しません。220項目は引き続き資料専用で、駒落ち専用の定跡や成立条件の照合が済んでいない名称を含みます。
